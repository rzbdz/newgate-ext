# 排障

先跑 `newgate doctor`。它查配置、provider、端口、接管和模块诊断——「不知道哪儿
不对」时它是第一条命令。下面按**你看到的现象**分。

## 1. 上游回 400，正文里有 reasoning_content

这是本发行版存在的原因之一，不是新故障。少数上游要求把上一轮的思维链原样带回来
（或者反过来，带了就报错），而不同厂商的方言**不一样**：

| 上游 | 它要什么 |
| --- | --- |
| DeepSeek | 把 reasoning 带回来 |
| GLM | 往回传 thinking |
| Kimi 系 | 该模型始终思考，必须显式开 |

判据是**报错的原文**（不是模型名），所以补丁认得出来是哪一家。三类 400 都**不摘牌**
——它不是上游坏了，是这一发的形状不对。

如果它持续出现，看这两处：

```bash
newgate st          # 那几个补丁此刻是开着还是被关掉了
newgate debug on    # 下一发的完整报文落进 dump/
```

`dump/` 里是三联文件：客户端发来的、我们发出去的、上游回的。**它是唯一能定罪的
证据**，别的都是猜。

## 2. `probe` 说通，真实请求却 400 / 404

两种成因，都不是 bug：

**a. provider 只配了声明协议入口。** 分别测 anthropic 的 `/v1/messages` 与 openai
的 `/v1/chat/completions`，检查 `anthropic_url` 与通用 base URL 是不是都指对了。

**b. probe 发的是最小请求**（一条消息、`max_tokens: 4`、没有 tools、没有历史）。
它探不到**只在长对话或思考模式下才触发**的上游校验——reasoning 那条就是典型。
probe 验证的是「连通性 + 方言」，不是「这条长对话过得去」。把两者混起来，就会得到
「probe 说健康、为什么还被摘」这种错误期待。

## 3. 明明能用，却被摘牌了

```bash
newgate breaker      # 两段：被摘的（状态/账本/还要等多久/原因）+ 只计数没摘的
newgate probe        # 不等冷却，立刻用一次主动探活改结论
newgate tier normal  # 这个 binding 在链里排第几、是不是被 maxAttempts 截断
```

先看**账本**那一列：

| 账本 | 什么情况 |
| --- | --- |
| 可用性 | 连接超时 / 5xx / 流中断——真的不行 |
| 限流 | 429，20 秒起就回来 |
| 配置 | 401 / 403 / 404，**一次即摘**，去查 key / base / 模型名 |
| 请求形状 | **永不摘牌**，只累加计数（§1 那类 400 出现在第二段里） |

原因是「连续失败到阈值时会先做一次主动探活，探活说还通就不摘」。所以一条 binding
真的被摘了，意思是**被动流量和主动探活都说不通**：

- 只写「真实流量连续失败」→ 探活也跑了，但结论也是不通（或者没有探活器）；
- 写「诊断探活也不通」→ 双重证据，摘得没冤枉它；
- 「半开试探失败」→ 冷却期满后它拿到过一次真实试探名额，那一发也失败了。

**半开**是恢复机制：冷却期满放行**一次**真实请求试探，成功即合闸，失败则回闸并把
冷却翻倍（60s → 120s → … → 10 分钟封顶）。所以第二段的「还要等」对不上 60 秒基准
是正常的——那是退避之后的实际值。

第二段的「救回」列是反方向的记录：这条 binding 一共被探活从摘牌边缘拉回来过几次。
这个数字在涨而「可用性」账本一直是 0，说明它间歇性抖动但每次都证明还活着——不是
故障，是上游在喘。

`newgate metrics` 里 `breaker.skipped.shape_error` 是 §1 那类 400 的计数器。

## 4. 接管了，客户端却还在直连

```bash
newgate status        # 四态：生效 / 声明了没生效 / 关过却没放开 / 直连
newgate doctor
```

按顺序查：

1. **PATH 顺序**——shim 那层在不在真的可执行文件前面；
2. **shell 里的旧变量**——已经存在的 `ANTHROPIC_BASE_URL` 这类会盖过配置；
3. **OpenCode 的配置**有没有被另一个工具覆盖；
4. **重开 shell**——PATH 改动对新开的终端才生效。

## 5. 重启了，行为却没变

`newgate version` 显示的是 **CLI 文件**的版本，它**不证明 daemon 换了血**（daemon
是另一个进程）。真正要看的是：

```bash
md5sum /proc/<pid>/exe /path/to/newgate
```

两个摘要不一致，说明升级没接上。另外核一下 `newgate plugin` 的**模块数**——它跟着
规格书走，少了就是装错了那份发行版。

## 6. 权限错误

daemon 那个用户要能写 state、pid、lock、log 和 thinkcache。目录建议保留 group 继承
位，文件需要 daemon 所在组可写。优雅交接回 500、或者冷层关不掉，通常是同一类问题。

## 7. Fallback 不是你想的那条链

```bash
newgate tier normal       # resolver 的输出：链、顺序、谁被跳过、为什么
newgate metrics           # chain.step_failed 与 chain.failover
```

再**从响应头确认最终 route**。不要盯着 profile 的文本猜链——`naked` 之类的运行期
开关、被摘牌的 binding、`maxAttempts` 截断都会改掉实际走的那条，而那些都不在文件里。

## 8. 请求被改坏了

以 `dump/` 的三联文件为**唯一**报文证据：对比客户端发来的和我们发出去的，找到具体
是哪一处拼接；再用日志的 notes 确认它是 schema repair、special treatment 还是
model rewrite 干的。

三类改写都能在运行期关掉（`newgate st`），所以定位到之后不用改代码就能先绕过。
