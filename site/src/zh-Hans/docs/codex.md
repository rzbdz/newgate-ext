# Codex 模式

Codex 与另外两家不一样，搞清楚这一点它的两种模式就自洽了：

> **Codex 的模型目录编在它自己的二进制里。**

`codex debug models` 会打出九个模型，而它**从不问服务端要**。实测把它的 provider
指向一个记账的假上游：`/v1/models` 一次都没被请求过——`--enable remote_models`、
provider 表里声明 `models_endpoint`、再配一个 `env_key`，三条都试了，假上游始终
收到 0 条。

所以「把我们的档位塞进 `/v1/models`、让它自己的选择器里出现档位」这条路**不存在**。
`config.toml` 里只能写一个模型名，于是「在 codex 里换模型」这件事一开始是做不到的。

## 两种模式

`newgate on codex` 接管时按模式决定往 `config.toml` 里写什么。网页面板上那张
**Codex 模型名**卡上有那个切换按钮（只画「另一个」，因为当前那个画成按钮等于一个
点了不会改变任何事的按钮）。

### 接管模式（缺省）

往 `config.toml` 里写**档位名**：

```toml
model = "normal"
```

codex 只认这一个模型，换也换不动——但每一发都落到你配的那条链上。这是
2026-09-21 之前的唯一行为，所以它也是缺省：不变更任何人的现状。

### 改名模式

往 `config.toml` 里写 **codex 自己的模型名**：

```toml
model = "gpt-5.6-luna"
```

然后在请求进来时，把这个名字认回我们的档位。用户在 codex 里按 `/model` 选中谁，
就落到我们哪一档——**这就是「里面无法切模型」的解法**。

## 那张表：codex 的哪个名字算哪一档

它是网页面板上的一张卡（**Codex 模型名**），也是 `~/.config/newgate/codex-models.json`
这份文件。出厂那五条按 codex 自己的 priority 排：最能干的给 `heavy`，最便宜的给
`light`。

| codex 的模型名 | 落到 |
| --- | --- |
| `gpt-6-astra` | heavy |
| `gpt-5.6-sol` | normal |
| `gpt-5.6-terra` | normal |
| `gpt-5.6-luna` | normal |
| `gpt-5.5` | light |

三条规矩，都是「不这么定就会静默出错」的那种：

- **所见即所得**：界面上保存的是**整张表**，所以删掉一行就是删掉了（出厂值不会
  把它顶回来）。文件里 `models` 一旦存在，它就是全部。
- **加一行、删一行都不用重启**：改完下一次请求就按新表认。
- **空名字、空档位、两行同名都会被拒**：这三种都能存下去，然后静静地什么都不做
  （匹配不上、保存后那一行自己消失、后一行永远轮不到）——拒绝比静默强。

codex 出了新模型时，加一行就行——**不用等我们发版**。哪个新名字该算哪一档，那
是你自己的取舍。

## 别的客户端不受影响

上面那张表只在**改名模式**下登记成动态档位。理由是一条实测出来的耦合：这些名字
一旦登记，`IsKnownRole` 就为真，于是「具体模型名反解回它所属档位」那条路被短路
——而那条路正是别的客户端点名 `gpt-5.6-terra` 时依赖的东西。所以它跟着模式走：
改名模式是你明确要过的形态，那时你要的就是「codex 的名字 = 档位」。
